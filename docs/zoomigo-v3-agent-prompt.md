# Build Zoomigo v3: Team World

Integrate the current zmap world runtime and modular Avatar Studio into `dafepro/fc-workout-pwa` as a new, independent v3 team lounge, working title **Team World**. Deliver a working, tested integration—not just a plan. This is a fresh successor to the alpha Canvas v2 lounge; no old room, placement, coordinate or avatar-data migration is required. Preserve unrelated Zoomigo account and training functionality. Do not build a legacy fallback or dual-write bridge.

Start by reading each repository's AGENTS.md and current source-of-truth docs. Inspect and record both checked-out commits. In zmap, read `examples/hub/architecture.html`, `docs/api.md`, `docs/operations.md`, `docs/multiplayer-coverage.md`, `docs/shared-performances.md`, and `avatar-studio/README.md` plus its contracts, accessory-fitting, wielding and motion docs. Read the original intent/specs/handoff as background; this fresh-v3 instruction supersedes their migration requirements. Reconcile historical status entries against current code and test evidence. Audit Zoomigo's actual lounge routes, authentication, team authorization, deployment, inventory and appearance storage before choosing adapters.

Keep these boundaries:

- **Zoomigo** owns identity, team membership, private room access, inventory/unlocks, approved appearance choices, persistence and all reward/training policy.
- **zmap** owns movement, real-height terrain, collisions, shared toy/action simulation, room synchronization, host recovery and placement mechanics. Its browser simulation host is untrusted for valuable outcomes.
- **@zmap/avatar-studio** owns validated modular appearance, fitting, animation, equipment grips and presentation. Its customization UI is a separate consumer, not required inside the world engine.
- **The Zoomigo integration layer** maps approved recipes to characters and accepted simulation state to animation. Use public contracts; fix missing reusable capabilities upstream rather than duplicating or forking the engine inside Zoomigo.

Build a lazy-loaded Team World route with the current courtyard/Fieldwork content as the first playable map: click/tap path movement, joystick, sprint, shared balls, cannon, field tools, emotes and draw/stow. Include an integrated appearance editor backed by approved catalogs and app-owned saved recipes. Preserve the existing angular cel/ink style, current walking improvements, accessory fitting and exact one-/two-hand grips. Use the established imagegen → front/side/top references → interactive Blender → in-engine inspection pipeline if new assets are necessary.

Replace example identities/tokens and the example file store with real app adapters: short-lived room-scoped credentials, membership revalidation, explicit origin allowlist, safe roster projection and transactional durable edits with ownership/entitlement checks, revision CAS and stable idempotency receipts. Treat identity.appearance as an app-resolved approved appearance key; do not cram recipe JSON into it. Keep transient actions out of reward and inventory authority. Use versioned assets and compatible client/relay/catalog releases; fail clearly on invalid content instead of silently substituting assets. Dispose all world, input, network and graphics resources on route exit. Loading, denial and failure states must leave the rest of Zoomigo usable.

Both packages are currently private local packages, not assumed npm releases. Establish and verify reproducible pinned package delivery and static asset serving in Zoomigo CI. Account for a persistent WebSocket relay and one writer per room; do not assume a stateless deployment or multiple uncoordinated relay replicas will work. Document database write deadlines, unknown-outcome reconciliation, service restart behavior and a pilot disable/rollback procedure that preserves new v3 data. This is deployment rollback, not Canvas conversion.

Track implementation and acceptance evidence in the repositories. Test real separate authenticated users, cross-team/expired-access denial, same-user tab replacement, late join, simultaneous tool interactions, host closure/stall, reconnect, sprint release, room isolation, persisted layout after restart, lost edit acknowledgments, saved appearance validation and repeated route mount/unmount. Review all movement directions with held gear. Run package, unit and browser suites appropriate to the changes. Qualify the proposed full-room phone/network/load/cost budgets on named hardware; desktop CI and the existing 20-socket test do not establish mobile production readiness. State unmeasured targets explicitly.

Proceed in working increments, resolve ordinary design choices autonomously, and finish with a runnable demo, integration docs, tests, measured limitations and release steps. Commit and push zmap only as dafepro using repository-local Git identity/credentials; follow Zoomigo's own repository rules without changing machine-wide accounts.
